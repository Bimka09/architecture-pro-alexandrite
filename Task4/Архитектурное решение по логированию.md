# Архитектурное решение по логированию

## Список логов уровня INFO для сбора

Онлайн-магазин:
    - Создание заказа: время, user_id, order_id, статус (INITIATED)
    - Загрузка файла 3D-модели: время, user_id, order_id, размер файла, формат, статус (FILE_UPLOADED)
    - Отправка заказа: время, user_id, order_id, статус (SUBMITTED)
    - Запросы к API: время, endpoint, method, response_time, status_code, user_id
    - Аутентификация: время, user_id, action (login/logout), IP-адрес, user_agent

CRM:
    - Подтверждение заказа: время, manager_id, order_id, статус (MANUFACTURING_APPROVED)
    - Закрытие заказа: время, manager_id, order_id, статус (CLOSED)
    - Работа с клиентами: время, manager_id, customer_id, action_type
    - Обработка сообщений RabbitMQ: время, queue_name, message_id, processing_result

MES:
    - Расчёт стоимости: время, order_id, calculation_time, polygon_count, price, статус (PRICE_CALCULATED)
    - Начало производства: время, operator_id, order_id, статус (MANUFACTURING_STARTED)
    - Завершение производства: время, operator_id, order_id, статус (MANUFACTURING_COMPLETED)
    - Упаковка: время, operator_id, order_id, статус (PACKAGING)
    - Отправка: время, operator_id, order_id, shipping_company, статус (SHIPPED)
    - API-запросы от внешних клиентов: время, client_id, endpoint, response_time, status_code

RabbitMQ:
    - Сообщения в очереди: время, source_system, target_system, message_type, order_id, processing_status

### Дополнительные уровни логирования

    - WARN:  Деградации (медленные запросы, повторные попытки обработки, переполнение очередей RabbitMQ и т.д)
    - ERROR: Ошибки, приводящие к невозможности выполнения операции (ошибки расчёта стоимости / недоступность внешних сервисов / ошибки валидации файлов и т.д)
    - FATAL: Невозможность запустить сервис
    - DEBUG: Детальная информация для разработки (только в dev-окружении)

## Мотивация

Текущее состояние не позволяет эффективно диагностировать инциденты и управлять SLA по заказам. Логирование вводится как слой наблюдаемости, обеспечивающий разбор проблем и переход к проактивному мониторингу.

Технические метрики решения:
    1. MTTR: снижение за счёт наличия полной трассы событий по заказу
    2. MTTD: снижение до минут за счёт алертинга по логам
    3. Error Rate: контроль и снижение за счёт раннего обнаружения деградаций
    4. Message Processing Time: время обработки сообщений в очередях

Бизнес-метрики решения:
    1. Доля потерянных заказов: снижение за счёт отслеживания всех переходов статусов
    2. Время обработки заказов: сокращение за счёт контроля за заказом на каждом этапе
    3. Количество клиентских жалоб: снижение за счёт проактивного обнаружения проблем
    3. Стоимость обработки инцидента: снижение за счёт ускорения диагностики

Приоритизация внедрения:
Первая очередь:
    1. MES: Здесь происходят ключевые изменения статусов заказа, ошибки приводят к прямым финансовым потерям, а состояние без логов восстановить невозможно.
    2. RabbitMQ: Асинхронное взаимодействие имеет под собой основной риск потери или дублирования сообщений. Без логов невозможно отследить цепочку доставки события.
    3. Онлайн-магазин API: Является точка входа всех заказов клиентов. Здесь логи необходимы для анализа пользовательского поведения и ошибок

Вторая очередь:
    1. CRM: влияет на бизнес-процессы, но не является источником первичных событий
    2. Пользовательские интерфейсы: Используются для UX-аналитики и корреляции и не являются критичными для восстановления состояний бизнес-процессов

## Политика хранения логов

elasticsearch-индексы:
    - logs-mes-api-{YYYY.MM.DD}
    - logs-crm-api-{YYYY.MM.DD}
    - logs-shop-api-{YYYY.MM.DD}
    - logs-rabbitmq-{YYYY.MM.DD}
    - logs-security-{YYYY.MM.DD}

| **Тип логов**          | **Уровень** | **Период хранения** | **Размер (оценка)** | **Причина**                 |
|:-----------------------|:------------|:--------------------|:--------------------|:----------------------------|
| Бизнес-события         | INFO        | 90 дней             | ~10 GB/месяц        | Анализ трендов, аудит       |
| Ошибки приложения      | ERROR       | 180 дней            | ~5 GB/месяц         | Статистика инцидентов       |
| Доступ и безопасность  | ALL         | 365 дней            | ~1 GB/месяц         | Соответствие требованиям    |
| Производительность     | DEBUG       | 30 дней             | ~50 GB/месяц        | Отладка, только dev         |
| Аудит операций         | INFO        | 730 дней            | ~20 GB/месяц        | Соответствие требованиям    |  

## Политика безопасности

Обработка чувствительных данных:
    - Исключение из логов: пароли, токены аутентификации, полные номера карт
    - Маскирование: частичное скрытие персональных данных
    - Хеширование: для анализа данных, не треующих точного сопосотавления с пользователем, user_id заменяется на необратимый хеш для анонимизации

Контроль доступа:
    - Разработчики: полный доступ к техническим логам (без персональных данных)
    - Поддержка: доступ к логам заказов и пользовательским действиям
    - Менеджеры: доступ только к агрегированным метрикам и дашбордам
    - Аудит: все действия в системе логирования протоколируются

## Алертинг

Критичные алерты:
    - Ошибки расчёта стоимости в MES
    - Недоступность RabbitMQ >1 минуты
    - Рост времени ответа API >5 секунд
    - Переполнение очередей сообщений

Предупреждения:
    - Медленные запросы >3 секунд
    - Необычный рост нагрузки (+50% от базовой)
    - Ошибки загрузки файлов >10% от общего количества

## Превращение в систему анализа логов

Автоматические проверки:
    - Резкий рост запросов: если RPS вырос в 3+ раза за 5 минут
    - Массовые ошибки: если error rate >5% в течение 2 минут
    - Застрявшие заказы: если заказ не меняет статус >24 часов

Машинное обучение (будущее развитие):
    - Предсказание узких мест на основе исторических данных
    - Автоматическое выявление новых типов проблем
    - Корреляционный анализ между метриками разных систем
