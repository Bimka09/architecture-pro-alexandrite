# Архитектурное решение по трейсингу

## Мотивация

В распределённой цепочке обработки заказа отсутствует сквозная наблюдаемость. Асинхронность и разрывы контекста делают невозможным точный ответ на вопросы:
    - где застрял заказ;
    - был ли он потерян;
    - какой шаг деградирует по времени.

Цель — обеспечить end-to-end трассировку каждого заказа с возможностью точечной диагностики.

## Системы, покрываемые трейсингом

Трейсинг внедряется в следующие компоненты:
    - Shop API — входная точка (создание заказа)
    - MES API — расчёт, производство, статусы, загрузка и обработка моделей
    - RabbitMQ — транспорт асинхронных событий
    - CRM API — обработка клиента и финализация

## Зоны возможной потери заказов

1) Публикация сообщения в RabbitMQ (ошибка/ретрай/потеря)
2) Обработка сообщения потребителем
3) Расчёт стоимости в MES
4) Смена статуса заказа
5) Загрузка/обработка 3D-файла в MES API и S3 (I/O, ошибки парсинга)

Каждый из шагов должен иметь свой span.

## Модель трейса

1) trace_id — идентификатор трейса
2) span_id — идентификатор шага
3) order_id — ключевая бизнес-сущность
4) message_id — для RabbitMQ
5) service_name — имя сервиса
6) operation_name — операция
7) status — success / error / timeout
8) error_message — текст ошибки
9) start_time — время начала
10) end_time — время окончания
11) queue_name - наименование очереди

## Влияние на метрики

Технические
Latency: время обработки запроса end-to-end
MTTD / MTTR: Сокращение времени обнаружения и устранения инцидентов
Error Rate by Partner: Мониторинг качества входящих запросов через API

Бизнес
Order SLA: время выполнения заказа
Orders Conversion: процент купивших от общего кол-ва пользователей
Order Loss Rate: Снижение процента «потерянных» заказов

## Предлагаемое решение

Для реализации используем стандарт OpenTelemetry, так как текущий стек состоит из разных языков (Java, C#, JavaScript).

Архитектура:

Collector: OpenTelemetry Collector для сбора данных.
Storage & UI: Jaeger для хранения и визуализации трейсов. Grafana для дашбордов
Интеграция: Доработка заголовков сообщений в RabbitMQ для проброса trace_id.

## Построение трейса

Корневой спан создаётся в Shop API при обработке входящего HTTP-запроса. При выполнении последующих синхронных вызовов к MES API и CRM API формируются дочерние спаны с сохранением исходного trace_id. Управление созданием и связностью спанов обеспечивает OpenTelemetry SDK, подключённый в сервисах.

Разрыв контекста при асинхронных взаимодействиях устраняется за счёт передачи trace_id в сообщениях RabbitMQ. При обработке этих сообщений контекст извлекается, и на его основе корректно продолжается трейс с созданием соответствующих спанов.

## Компромиссы

Стоимость хранения: Хранить 100% трейсов при росте нагрузки может быть дорого. На начальном этапе будем использовать 100% семплирование, но при кратном росте перейдем на Probabilistic Sampling (например, хранить только 10% успешных и 100% ошибочных трейсов).

Производительность: Добавление трейсинга создает небольшой оверхед по использованиб ресурсов. Учитывая проблемы с производительностью MES db, внедрение агентов трейсинга должно сопровождаться оптимизацией запросов к БД.

## Безопасность

    1) Аутентификация и авторизация: Доступ к Jaeger UI предоставляется только сотрудникам с валидной корпоративной учётной записью через OAuth2 провайдер.
    2) Сетевые ограничения: Доступ к Jaeger UI и API разрешён только из внутренней сети компании
    3) Защита передаваемых данных: TLS 1.3 для всех коммуникаций между агентами трейсинга и коллектором. mTLS для взаимной аутентификации компонентов системы
    4) Мониторинг доступа: логирование попыток входа в систему, просмотра трейсов, экспорта данных
    5) Маскирование персональных и чувствительных данных
